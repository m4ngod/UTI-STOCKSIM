# UTI-STOCKSIM 论文撰写建议整合版

更新时间：2026-05-08

本文档已将两次论文撰写建议合并为统一版本。第一版建议给出了论文定位、题目、核心论点和完整章节大纲；第二版建议根据项目最新进展修正了 Evidence Runner 的表述。整合后的最终口径是：

不是把项目写成“我做了一个交易软件”，而是写成：

> 本文面向机器学习交易策略训练中的环境失真与评估证据不足问题，设计并实现了一个具有真实交易语义、多智能体行为生态、模型训练闭环与证据门控机制的交易仿真研究平台 UTI-STOCKSIM。

这会把论文从“项目说明书”升级为“研究型工程论文”。

当前最新项目状态必须这样表述：

> UTI-STOCKSIM 已经不是普通 Python GUI 或简单回测项目，而是一个包含交易 runtime、PostgreSQL-first 持久化、多智能体训练、Arena/PBT 和 Evidence Runner 的研究平台。项目最新状态不是“Evidence Runner 还没跑通”，而是“Evidence Runner 已经生成 live PostgreSQL/runtime evidence package，但 package 状态仍为 complete / no_go”。这说明系统已经具备真实 runtime/database 证据生成能力，同时证据门控能够正确阻止证据不足的模型进入父代继承、模型晋升或研究结论。

论文不要主张“训练出了可以实盘赚钱的模型”。更强、更稳、更容易答辩的论点是：

> 本文解决的是交易模型训练环境可信度不足的问题，而不是直接证明某个模型已经具备真实市场盈利能力。

# 2. 论文核心论点

论文核心论点建议写成：

> 传统价格序列回测或简化强化学习环境忽略订单簿、撮合、账户冻结、交易费用、T+1、卖空约束、散户行为噪声和市场时钟等真实交易约束，容易导致模型在玩具环境中学到不可迁移策略。本文设计并实现 UTI-STOCKSIM，使模型必须通过正式订单、账户、风控和撮合路径参与市场，并通过 retail 行为生态、Arena 对抗训练、Observation/Action/Reward 契约、PBT 继承和 Evidence Runner 证据门控形成完整训练与评估闭环。

**本文构建了一个面向机器学习交易策略研究的可信仿真实验基础设施。**

# 3. 必须更新后的 Evidence Runner 论文口径

两次建议的最大差异在 Evidence Runner 状态。最终论文必须采用最新口径。

旧口径：

```text
Evidence Runner schema、runner、gate 已形成，但 live PostgreSQL/runtime 长 Arena series 尚未完成，因此当前 No-Go。
```

新口径：

```text
Task 101 已完成 live PostgreSQL/runtime evidence package 构建，能够通过真实 build_app_context()、ArenaExperimentRunner.run_generations(...)、RuntimeModelAgent、TrainingArenaService、TrainingEpisodeService 和 PostgreSQL ORM 生成 database/runtime 证据包。当前 package 状态为 complete / no_go。No-Go 不再是环境或链路阻塞，而是 strict evidence gate 在真实 runtime/database 证据上发现 calibration、exploit test、paired sensitivity 等上游证据仍不满足通过条件。
```

这一变化不是削弱论文，而是增强论文。因为这说明系统已经从“能不能跑通”升级到“真实证据是否足够支撑研究结论”。

必须写清楚：

- `complete` 表示 evidence package 所需槽位已生成并可被聚合。
- `no_go` 表示至少存在未通过的 evidence gate。
- `complete / no_go` 并不矛盾。
- 它说明工程链路已经可运行，但研究结论尚不能放行。
- 这是 Evidence Runner 正常工作的表现，不是系统失败。

# 4. 摘要写法

摘要建议按四段写。

第一段：研究背景。

机器学习和强化学习逐渐用于量化交易策略研究，但许多训练环境只基于价格序列，缺少订单簿、账户、撮合、费用、交易规则和市场参与者行为等真实交易语义。

第二段：问题。

简化训练环境可能导致模型在仿真中表现良好，却在真实市场中因为冻结资金、成交规则、费用、流动性、T+1、卖空约束或市场噪声而失效。因此，交易策略研究需要一个更接近真实交易约束、可观察、可复现、可审计的仿真训练平台。

第三段：方法。

本文设计并实现 UTI-STOCKSIM，一个桌面级交易仿真、多智能体训练与研究证据平台。系统包含真实交易 runtime、订单簿撮合、账户与持仓管理、retail agent 行为生态、模型 Observation/Action/Reward 契约、Arena/PBT 训练闭环、PostgreSQL-first 持久化和 Evidence Runner 证据门控机制。

第四段：结果与意义。

系统实现了从市场仿真、agent 运行、模型训练、实验记录到证据门控的闭环。最新 live PostgreSQL/runtime evidence package 已能从真实 runtime/database 中读回训练、订单、成交、agent binding 和账户权益等事实，并生成 `complete / no_go` 的证据包。实验表明，平台已具备真实运行证据生成能力，但 calibration、exploit test 与 paired sensitivity 等上游证据仍未通过，因此本文不将当前结果解释为模型研究有效性通过，而将其作为可信证据门控机制的阶段性验证。

关键词：

**交易仿真；多智能体系统；强化学习；订单撮合；行为金融；量化交易；Evidence Runner；PostgreSQL**

# 6. 第 1 章 绪论

## 1.1 研究背景

写机器学习交易策略训练面临的问题：

传统回测通常把市场简化成价格序列，策略只需要决定买卖信号。但真实交易中，策略会受到订单簿深度、撮合机制、账户资金、持仓冻结、交易费用、T+1、卖空约束、散户噪声和市场时钟影响。如果训练环境过于简化，模型可能只学到玩具环境中有效的行为。

## 1.2 研究问题

明确提出论文要解决的问题：

1. 如何构建一个比传统回测更接近真实交易运行时的仿真环境？
2. 如何让模型在训练时面对订单、账户、撮合、费用、风控和交易日规则？
3. 如何构建稳定但不死板的 retail agent 行为生态？
4. 如何让多个模型 agent 在同一市场环境中训练、对抗、评估和继承？
5. 如何避免仅凭 leaderboard 收益就错误判断模型有效？

## 1.3 研究目标

建议写成：

本文目标是设计并实现一个面向机器学习交易策略训练的真实交易语义多智能体仿真平台。平台需要支持多标的交易、订单簿撮合、账户与持仓管理、费用与冻结、retail agent 行为生态、模型 agent 接入、Arena 训练、PBT 继承、实验持久化和证据门控。

## 1.4 本文主要工作

建议写 5 点：

1. 设计真实交易语义 runtime，使所有 agent 必须通过订单、撮合、账户、风控和结算路径参与市场。
2. 构建 retail agent 行为生态，用行为家族、性格参数和状态变量生成市场噪声。
3. 设计模型交互契约，将 Observation、Action、Reward 与交易运行时解耦。
4. 实现多模型 Arena、PBT 继承、checkpoint 和 lineage 训练闭环。
5. 引入 Evidence Runner / Evidence Gate，使模型晋升和研究结论不只依赖收益排名。

## 1.5 论文组织结构

简要介绍后续章节即可，不要写得太长。

# 7. 第 2 章 相关技术与理论基础

这一章不要写太散，要服务系统设计。

## 2.1 传统回测框架及其局限

写传统回测通常关注历史价格、技术指标、收益曲线，但缺少微观交易约束，特别是订单簿、成交可达性、冻结资金、手续费和实际执行风险。

## 2.2 订单簿与撮合机制

介绍限价单、市价单、买卖盘口、价格优先、时间优先、成交、撤单、部分成交等概念。

## 2.3 多智能体市场仿真

介绍 agent-based simulation 思想：市场不是一个单一价格序列，而是多个参与者行为共同形成的结果。

## 2.4 强化学习在交易策略中的应用

介绍状态、动作、奖励、策略、episode、Actor-Critic、Recurrent Policy 等概念。项目当前用 `ppo_lstm_v1` 作为 baseline，重点不是证明它最优，而是验证观察、决策、下单、成交、奖励、学习、评估和继承闭环。

## 2.5 实验可复现与模型评估

引出 Evidence Runner：交易模型不能只看收益，还需要 baseline、hidden evaluation、exploit test、fee/impact sensitivity、parent gate 和 research acceptance lock。

# 8. 第 3 章 系统需求分析与总体设计

## 3.1 系统需求分析

功能需求：

1. 支持多标的模拟交易。
2. 支持订单提交、撤单、撮合、成交和拒单。
3. 支持账户现金、冻结资金、持仓、费用和结算。
4. 支持 retail agent 和 model agent。
5. 支持 Arena 训练、排行榜、checkpoint 和 lineage。
6. 支持 K 线、快照、成交和账户状态可视化。
7. 支持实验数据持久化和证据记录。

非功能需求：

1. 可扩展性。
2. 可观察性。
3. 可复现性。
4. 数据一致性。
5. 交易语义真实性。
6. 实验结果可追踪。

研究性需求：

1. 模型不能绕过 runtime truth。
2. leaderboard 不能直接等于模型有效。
3. 训练结果必须有 evidence artifacts 支撑。

## 3.2 系统总体架构

建议放一张总架构图：

```text
PySide6 桌面应用层
  -> RuntimeGateway
  -> RuntimeQueryService / RuntimeCommandService
  -> Order / Account / Matching / Clock / Agent Runtime
  -> PostgreSQL Persistence
  -> Arena / PBT / Evidence Runner
```

也可以写成：

```text
桌面可视化与控制层
  -> 应用服务与控制器层
  -> RuntimeGateway 边界
  -> 交易运行时服务层
  -> 核心撮合与账户语义层
  -> PostgreSQL 持久化层
  -> Arena 训练与 Evidence Runner 评估层
```

## 3.3 系统模块划分

建议分为：

1. 交易运行时模块。
2. 市场数据与事件模块。
3. 账户与订单模块。
4. Retail agent 模块。
5. Model agent 与 Arena 模块。
6. 数据持久化模块。
7. 前端可视化模块。
8. Evidence Runner 模块。

## 3.4 关键设计原则

这一节很有答辩价值：

1. **Runtime Truth 原则**：订单、账户、成交、K线、快照来自同一套运行事实。
2. **Agent 不越权原则**：模型只能通过 Observation/Action/Reward 契约参与市场。
3. **收益不等于证据原则**：模型晋升必须通过 evidence gate。
4. **前后端边界原则**：GUI 不直接操作核心交易语义。
5. **可复现实验原则**：训练 episode、transition、checkpoint、lineage 必须持久化。

# 10. 第 5 章 Retail Agent 行为生态设计

这是论文的第二个亮点。

## 5.1 Retail Agent 的设计动机

写真实市场不是只有模型互相交易，还需要大量具有差异化行为的散户 agent 作为市场噪声、流动性来源和行为金融环境。Retail agent 用行为家族、性格参数和状态变量驱动市场噪声，而不是简单随机买卖。

## 5.2 行为家族设计

建议写：

1. 均值回归型。
2. 逢跌买入型。
3. 止盈型。
4. 流动性噪声型。
5. 动量型。
6. 随机扰动型。

## 5.3 性格参数设计

写：

1. 风险偏好。
2. 损失厌恶。
3. 勇敢程度。
4. 耐心。
5. 价格敏感度。
6. 持仓倾向。

“勇敢程度”可以定义为 agent 在亏损、波动、回撤或不确定环境下继续交易或加仓的倾向，很适合写进论文。

## 5.4 状态变量设计

写：

1. 当前现金。
2. 当前持仓。
3. 可卖数量。
4. 未成交挂单。
5. 近期盈亏。
6. 持仓时间。
7. 近期成交情况。

## 5.5 Retail Calibration 指标

写：

1. 买卖比例。
2. 双边挂单覆盖率。
3. 成交活跃度。
4. 持仓周期。
5. 价格波动特征。
6. 流动性状态。

## 5.6 本章小结

强调 retail 生态的作用不是精确预测真实散户，而是构建一个比随机噪声更稳定、更可调、更接近交易行为约束的背景市场。

# 11. 第 6 章 Model Agent 与 Arena 训练机制

## 8.3 Baseline、Hidden Evaluation 与 Exploit Test

Baseline 用来判断候选模型是否真正优于简单规则基线。

Hidden Evaluation 用来判断候选模型是否只适配训练世界。

Exploit Test 用来检查候选模型是否可能利用费用、时钟、成交边界、mark-to-market 或 order boundary 漏洞获利。

## 8.4 Paired Fee/Impact Sensitivity

写 paired sensitivity 的目的：

同一候选模型要在 base、high_fee、high_impact、low_liquidity 等配对世界中比较表现，避免模型只在低费用、低冲击、理想流动性下成立。

## 8.5 Strict Parent Gate 与 Research Acceptance Lock

写：

模型能否成为父代，不由收益单独决定，而由 evidence gate 决定。

研究结论能否成立，需要通过证据锁。不允许把未通过 live evidence 的结果写成研究通过。

## 8.6 Model Route Gate

写：

在 Evidence Runner No-Go 解除前，不升级 Transformer、GTrXL、复杂 MARL、historical replay、hybrid env 或 alpha-claim 路线。

## 8.7 Live Evidence Package 状态语义

这是第二次建议新增的重点。必须写：

> `complete` 和 `no_go` 可以同时成立。`complete` 表示 evidence package 所需槽位已被生成并可被 strict aggregate 聚合；`no_go` 表示其中至少存在未通过的 evidence gate。

论文里可以解释：

> 本文将 `complete / no_go` 视为 Evidence Runner 的有效工作状态，而不是系统失败。它表明证据门控机制能够区分“工程链路可运行”和“研究结论可信”两个层次。

## 8.8 Strict Aggregate 与旧格式 Artifact 拒绝机制

这一节也很有论文价值。

写：

证据失败不再使包本身变成 `incomplete`，缺失或 `not_available` 才表示包不完整。旧格式 artifact 也会被 strict aggregate 拒绝。仅有 `pass_fail=true` 而缺少以下字段时，不能被当作研究证据通过：

1. `source=live_postgresql_runtime`
2. `pass_gate`
3. `runner_version`
4. 可重算的 `artifact_hash`
5. 明确的 `source_run_ids`

这说明 Evidence Runner 不是只生成报告，而是对证据来源、runner 版本、hash 和 gate 语义进行严格校验。

```text
  -> Arena + PBT 跑通训练闭环
  -> PostgreSQL 保存实验事实
  -> Evidence Runner 防止错误晋升和虚假结论
  -> 最新 live package 为 complete / no_go，说明链路可运行但证据门控仍健康阻断
```

这条线一旦立住，项目就不是“做了一个交易软件”，而是：

> 构建了一个面向机器学习交易策略研究的可信仿真实验基础设施。

# 17. 最强答辩口径

可以直接背这段：

> 本项目最新状态不是“Evidence Runner 还没跑通”，而是“Evidence Runner 已经跑通 live PostgreSQL/runtime package，但研究证据仍然 No-Go”。这说明系统已经具备真实 runtime evidence 生成能力，同时 Evidence Gate 能够正确阻止证据不足的模型进入父代继承、模型晋升或研究结论。当前 No-Go 是健康的 No-Go，它证明平台不是用 leaderboard 收益包装模型有效性，而是将模型研究资格建立在 calibration、baseline、hidden evaluation、exploit test、paired sensitivity 和 strict parent gate 的独立证据之上。

如果老师问“为什么 No-Go 还算成果”，可以回答：

> 因为本文的目标不是宣称模型已经可用于实盘，而是构建一个可信训练与评估平台。`complete / no_go` 说明系统已经可以生成完整 live evidence package，并且能够拒绝证据不足的候选模型。对于交易模型研究来说，能够阻止不充分证据被误读为成功，本身就是平台可信性的核心体现。

如果老师问“你的创新点是什么”，可以回答：

> 创新点不是某一个模型，而是把真实交易语义 runtime、retail 行为生态、模型训练契约、Arena/PBT 训练闭环和 Evidence Runner 证据门控放到同一个平台中，使模型必须在更接近真实交易约束的环境中行动，并且必须通过独立证据审查才能被晋升或形成研究结论。

# 18. 写作禁区

不要这样写：

1. 不要写“本系统训练出了可实盘盈利模型”。
2. 不要写“Evidence Runner 已经 Go”。
3. 不要把 `complete / no_go` 写成失败。
4. 不要把 leaderboard 排名写成模型有效性证明。
5. 不要把 headless package 当成正式 live research evidence。
6. 不要忽略 `snapshots_1s` / `bars_1m` 为 0 对 calibration 的影响。
7. 不要为了好看把 No-Go 原因改轻。

应该这样写：

1. 系统已经具备 live runtime evidence package 生成能力。
2. 当前 No-Go 是由严格证据门控产生的健康阻断。
3. runtime/database 链路、训练记录、订单成交事实已经进入 live 验证阶段。
4. calibration、exploit test、paired sensitivity 仍需补齐。
5. 本文验证的是可信仿真实验基础设施，而不是实盘盈利模型。
