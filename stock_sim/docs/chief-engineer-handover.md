# UTI-STOCKSIM 总工程师接管文档

_生成时间：2026-03-22 16:04 (Asia/Shanghai)_

## 1. 接管结论

UTI-STOCKSIM 已经不是“单点功能开发阶段”的项目，而是一个正在从**可运行原型**向**可维护复杂系统**收束的交易仿真平台。

当前最正确的方向不是继续无节制堆功能，而是围绕以下三件事持续推进：

1. **结构收束**：减少重复入口、重复结构、兼容壳和历史分叉
2. **数据收束**：明确每个页面、字段、事件、状态的真实来源与权威性
3. **主链路稳定**：用测试锁住关键业务路径，使重构可以持续进行

---

## 2. 软件定位

该项目是一个面向股票/衍生品交易仿真的综合平台，核心目标是在尽量贴近真实交易语义的前提下，为研究、教学、策略实验、强化学习训练提供底座。

### 当前已覆盖的核心能力

- 多标的撮合
- 账户冻结 / 释放 / 成交结算
- 风控校验
- 融券卖空与回补
- IPO 集合竞价 / 自动开盘路径
- 事件总线驱动的数据传播
- 桌面前端可视化（PySide6 + pyqtgraph）
- 强化学习环境 / 策略实验能力
- 持久化与运行期数据管理

这意味着项目的工程性质更接近：

> **交易运行时内核 + 桌面应用层 + 数据/实验平台**

而不是传统意义上的“小型 Python GUI 项目”。

## 3. 当前总体架构判断

## 3.1 分层方向是对的

项目已经形成较清晰的层次：

- `core/`：撮合、订单簿、领域模型、核心规则
- `services/`：订单编排、账户结算、风险控制、费用、引擎注册等真实运行时服务
- `app/`：桌面前端、controller、panel、adapter、app-layer service
- `infra/`：事件总线、基础设施
- `persistence/`：ORM 与数据库模型
- `rl/`、`agents/`：强化学习与策略逻辑
- `docs/`：路线图、设计记录、当前工作状态、架构演进说明

这说明项目并非“完全无序”，而是已经进入**系统级治理阶段**。

## 3.2 当前主要问题不是“没有架构”，而是“架构收束尚未完成”

现阶段的关键问题包括：

- 仍存在兼容壳与历史残留结构
- 前端 detail 页的数据来源并不统一
- app-layer service 与 runtime service 在命名上存在潜在混淆
- 某些核心 orchestrator 已经过重，后续容易成为泥球
- 存储层路线正在从 SQLite 心智迁移为 PostgreSQL + Redis 分层，但代码尚未完全跟上

## 4. 当前代码逻辑掌握结果

## 4.1 前端性质：桌面前端 + 应用层，而不是传统 Web 前端

前端主要由以下部分组成：

- `app/ui/*`：真实窗口结构、导航、布局、样式
- `app/panels/*`：页面逻辑层
- `app/controllers/*`：面向页面的数据与操作控制层
- `app/ui/adapters/*`：Qt 渲染适配层
- `app/services/*`：前端应用层服务（缓存、拉取、聚合、DTO 提供）

因此后续开发不应套用传统浏览器前后端脑回路，而应明确区分：

1. **桌面 UI 渲染层**
2. **前端应用逻辑层**
3. **运行时业务后端**
4. **事件/DTO/桥接层**

## 4.2 后端运行时主链路已经形成真实语义中心

### `services/order_service.py`

这是当前订单生命周期的真实 orchestrator，负责：

- 基础校验
- 风控校验
- 费用估算与预冻结
- 主体冻结（现金/持仓）
- 动态路由到撮合引擎
- 成交后持久化与结算
- IOC / FOK 处理
- 事件广播与状态落库

### `services/account_service.py`

这是当前账户语义中心，负责：

- 账户创建 / 获取
- 持仓创建 / 获取
- `cash / frozen_cash / frozen_fee`
- `quantity / frozen_qty / borrowed_qty`
- 批量结算
- ledger 写入
- `ACCOUNT_UPDATED` 事件发布

### 结论

**后端已经具备“真实交易语义中心”**。这非常重要，说明系统后续可以围绕真实 runtime truth 去收束，而不是继续依赖 UI 侧的近似表达。

## 5. 已确认的项目收束方向

根据现有 docs 与代码状态，当前项目的正式收束方向可归纳为以下五个阶段。

## Phase 1：结构收束

目标：先让系统只有一套主骨架。

### 当前共识

- `app/ui/main_window.py` 是唯一真实主窗口
- `app/main.py` 应继续收缩为兼容/入口包装层
- 新功能不应再把结构责任加回 `app/main.py`

### 当前价值

这一阶段完成后，前端结构的“真入口”会清晰得多，后续修 UI 或修数据路径时，不再受历史双结构干扰。

## Phase 2：数据收束

目标：每个页面字段都清楚知道自己从哪里来。

### 当前典型问题：Market detail

Market detail 页面当前不是单一权威数据源，而是多个来源拼装：

- `snapshot`
- `order_book`
- `series`
- `trades`
- `holdings`

它们刷新方式、权威性、延迟特征并不一致。

### 当前判断

如果不先把字段契约讲清楚，那么所有“修 detail 页”“修 K 线”“修显示不一致”的工作，都会变成局部补丁。

## Phase 3：职责收束

目标：边界清晰，谁负责什么一眼能说清。

建议长期坚持以下边界：

- `core/`：撮合与领域模型
- `services/`：真实业务编排
- `app/controllers/`：前端应用控制
- `app/panels/`：页面逻辑
- `app/ui/adapters/`：Qt 渲染适配

## Phase 4：主链路稳定性收束

目标：锁住关键用户路径，使重构可持续。

重点链路：

1. 创建标的
2. 进入标的详情
3. 下单 → 撮合 → 成交 → 账户更新
4. snapshot 推送 → 市场列表刷新
5. K 线加载 → 详情展示
6. IPO / 卖空 / T+1 / 冻结资金等高风险流程

## Phase 5：文档与命名收束

目标：未来维护不再重复考古。

包括：

- 持续维护 `docs/current-work-status/*`
- 持续更新设计意图、边界、真实入口、真实数据源
- 对跨层同名对象补充说明或逐步改名

## 6. 当前系统最值得警惕的工程风险

## 6.1 `services/order_service.py` 已经过重

问题不在它当前不能用，而在于：

- 它已经承担过多编排责任
- 很容易成为后续新功能“顺手塞进去”的核心泥球
- 一旦测试覆盖不够，它会成为最高风险改动点

### 建议

短期内不强行大拆，但应明确未来拆分方向，例如：

- order normalization / validation
- freeze pipeline
- execution routing
- post-trade settlement orchestration
- persistence / event emission coordination

## 6.2 Market detail 数据真相尚未完全统一

这是当前前端维护性的核心风险之一。

如果一个页面表面统一、底层多源半同步，那么后续的：

- bug 定位
- UI 修复
- 性能优化
- 交互修复

都会变得代价很高。

## 6.3 app-layer service 与 runtime service 命名存在混淆风险

例如：

- `app/services/account_service.py`
- `services/account_service.py`

它们不是一回事，但名字非常像。

### 建议

后续要么：

- 在导入规范和文档中持续强提示
- 要么逐步改名，显式区分 app-layer / runtime-layer

## 6.4 存储层心智迁移尚未完成

docs 已明确推荐：

- SQLite：dev / test / demo
- PostgreSQL：authoritative business store
- Redis：hot-state / real-time cache layer

这个方向非常合理，也应该成为后续所有新设计的默认假设。

## 9. 总工程师执行原则

从现在开始，后续开发建议遵循以下原则：

1. **先保主链路，再谈新功能**
2. **先讲清数据真相，再修页面表现**
3. **先收束结构，再扩大复杂度**
4. **每次改动都明确属于哪个收束阶段**
5. **文档、代码、测试尽量同步推进**
6. **不让兼容层重新长成架构本体**
7. **不把 runtime truth 伪装成 UI approximation**

### 每次进入实现前先回答 4 个问题

1. 这次改动属于结构收束、数据收束、职责收束，还是主链路稳定？
2. 改动后谁是新的真实入口 / 真实数据源？
3. 会不会让兼容层重新膨胀？
4. 是否需要补测试与文档？

## 11. 一句话总判断

> UTI-STOCKSIM 现在最需要的不是“更快加功能”，而是“把已经长出来的复杂度收束成可维护系统”。

当前方向总体正确，接下来应以**结构清晰、数据诚实、主链路可测**为最高优先级。
