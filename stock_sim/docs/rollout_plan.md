# UTI-STOCKSIM 收束路线图

_Last updated: 2026-03-20_

本文档用于记录项目从“能跑的复杂系统”向“可维护的复杂系统”收束的执行路线。

核心原则：

1. 减少重复结构
2. 明确数据真相
3. 切清职责边界
4. 用测试锁住主链路
5. 持续同步文档

---

## 总目标

在不破坏现有可运行能力的前提下，逐步完成以下转变：

- 从多入口/兼容壳/历史分叉，收束为单一真实结构
- 从页面混合多套半同步数据源，收束为可解释、可追踪的数据契约
- 从“改一个点怕炸一片”，收束为“主链路有测试、重构可推进”的状态

---

## Phase 1：结构收束

目标：先让系统只有一套主骨架。

### 重点事项

- 明确 `app/ui/main_window.py` 是唯一真实主窗口
- 继续压缩 `app/main.py` 为纯入口 / 兼容壳
- 统一页面打开路径、面板注册路径、主窗口注册路径
- 清理残留兼容别名、旧入口假设、历史结构依赖

### 完成标准

- 新功能不再把结构责任加回 `app/main.py`
- 页面打开不再依赖多条互相重叠的路径
- 主窗口/工作区/详情页导航由单一结构负责

### 当前优先级

最高

---

## Phase 2：数据收束

目标：每个页面字段都清楚知道自己从哪里来。

### 重点事项

- 明确 Market detail 各字段契约：
  - `snapshot`
  - `order_book`
  - `series`
  - `trades`
  - `holdings`
- 区分前端应用层服务与后端运行时服务：
  - `app/services/*`
  - `services/*`
- 避免一个页面无文档地拼装多条半同步数据路径

### 完成标准

- 能按字段解释详情页数据来源
- 调试时能准确定位是 snapshot 路径、bars 路径还是事件路径问题
- 关键页面不再依赖“感觉上差不多”的数据拼接

### 当前优先级

高

---

## Phase 3：职责收束

目标：谁负责什么，边界清晰，不互相偷活。

### 目标边界

- `core/`：撮合与领域模型
- `services/`：真实业务编排
- `app/controllers/`：前端应用控制
- `app/panels/`：页面逻辑
- `app/ui/adapters/`：Qt 渲染与交互适配

### 完成标准

- 改撮合/结算不需要顺手改 UI
- 改 UI 样式不需要碰交易语义
- 业务逻辑不在多个层级重复实现

### 当前优先级

高

---

## Phase 4：主链路稳定性收束

目标：锁住关键用户路径，让重构可持续。

### 关键链路

1. 创建标的
2. 双击/进入标的详情
3. 下单 → 撮合 → 成交 → 账户更新
4. snapshot 推送 → 市场列表刷新
5. K线加载 → 详情展示
6. IPO / 卖空 / 冻结资金等高风险流程

### 完成标准

- 关键链路至少有单元/集成/端到端中的一种覆盖
- 修复局部问题不会轻易回归到主流程
- 结构重构可以在测试保护下持续推进

### 当前优先级

中高

---

## Phase 5：文档与命名收束

目标：减少未来维护中的重复考古成本。

### 重点事项

- 继续维护 `docs/current-work-status/*`
- 在关键模块文档中记录“当前真入口 / 当前真数据源”
- 对跨层重名对象补充说明，必要时逐步改名
- 每次结构性变更同步更新文档

### 完成标准

- 后续开发可以依赖文档续接，而不是重复猜测
- 关键设计意图、边界、迁移方向有持续记录

### 当前优先级

中

---

## 推荐推进顺序

### 第一阶段

- 完成 MainWindow 唯一化
- 继续压缩 `app/main.py`
- 统一页面/面板打开路径
- 将入口层逐步从兼容壳默认心智切换到真实 MainWindow / 本地入口封装

### 第二阶段

- 梳理 Market detail 字段契约
- 对齐 Account 页面与真实冻结字段语义
- 对齐 Orders / Account / runtime 的订单生命周期表达
- 让前端 contract 更诚实地表达非权威字段、冻结语义与生命周期阶段
- 写清 app-layer / runtime-layer 边界

### 第三阶段

- 补关键路径回归测试
- 做关键用户流程 smoke / e2e 验证
- 文档与代码持续同步

---

## 一句话总结

> 收束不是重写，而是把重复的删掉、把模糊的讲清、把关键路径锁住。
