# UTI-STOCKSIM 项目细节与论文关键信息提取

本文档用于辅助毕业论文写作，重点提取 UTI-STOCKSIM 项目中应当写入论文的核心事实、设计思路、模块边界、实验结果与研究边界。写作时应优先使用本文档中的“可写结论”和“边界表述”，避免把工程验收结论夸大为真实市场盈利能力或高层级研究结论。

## 1. 论文题目建议

推荐题目：

> 面向机器学习交易策略训练的真实交易语义多智能体仿真平台设计与实现  
> —— 基于 UTI-STOCKSIM 的系统实现与证据门控研究

题目中的关键词应体现四个重点：

- 真实交易语义：订单、撮合、账户、资金冻结、费用、T+1、卖空约束等不被简化掉。
- 多智能体仿真：retail agent 与 model agent 在同一市场中交互。
- 模型训练平台：通过 Observation / Action / Reward 契约与 Arena 训练闭环接入模型。
- 证据门控：模型表现不能只看收益排名，而要通过 Evidence Runner 进行结构化审查。

## 2. 项目一句话定位

UTI-STOCKSIM 是一个桌面级交易仿真、多智能体训练与研究证据平台。它不是简单股票行情演示器，也不是传统回测脚本集合，而是以真实交易语义 runtime 为核心，以 PySide6 桌面应用为观察与控制台，以 PostgreSQL 为运行事实底座，以 Arena/PBT 和 Evidence Runner 支撑模型训练与研究证据审查的仿真系统。

论文中可写成：

> 本系统围绕机器学习交易策略训练中的环境失真、市场背景过于理想化、模型评价证据不足等问题，构建了一个包含真实交易运行时、多智能体市场参与者、模型训练契约、实验事实持久化和证据门控机制的仿真平台。

## 3. 研究背景中应强调的问题

论文第一章可以围绕以下问题展开：

1. 传统回测通常只基于历史价格序列，弱化了真实交易过程中的订单簿、成交可达性、账户冻结、手续费、T+1、卖空和流动性约束。
2. 强化学习模型如果在过度理想化环境中训练，可能学习到利用仿真漏洞的策略，而不是稳健的交易行为。
3. 单纯使用 leaderboard 收益或单次实验收益评价模型，容易产生过拟合、环境漏洞利用和研究结论误判。
4. 交易策略研究需要的不只是“能跑模型”，还需要可观察、可复现、可审计的 runtime facts 和 evidence artifacts。
5. 因此，平台需要把真实交易语义、多智能体市场背景、模型训练闭环和证据门控机制放到同一套系统中。

可写研究问题：

- 如何构建比传统价格序列回测更接近真实交易过程的训练环境？
- 如何让 model agent 必须经过订单、账户、风控和撮合路径，而不能直接修改收益？
- 如何构建稳定但不死板的 retail agent 背景市场？
- 如何记录训练、订单、成交、账户和市场数据，使实验可追踪、可复现？
- 如何避免把收益排名直接误写成模型研究有效性？

## 4. 系统总体架构应写的六层结构

论文第三章可以把系统总体架构写成六层：

1. PySide6 桌面可视化与控制层  
   包括 Market、Symbol Detail、Orders、Account、Agents、Leaderboard、Clock、Arena、Evidence Board 等面板。

2. 应用服务与控制器层  
   负责把用户操作转为后端调用，组织 Panel、Controller、App Service 与 EventBridge。

3. RuntimeGateway 边界层  
   app 层访问 runtime 的统一边界。读侧通过 RuntimeQueryService，写侧通过 RuntimeCommandService，避免 UI 直接操作 ORM 或撮合引擎。

4. 交易运行时服务层  
   包括 OrderService、AccountService、InstrumentService、SimClock、AgentService、TrainingArenaService 等，负责编排市场、账户、订单、agent 和训练过程。

5. 核心撮合与账户语义层  
   包括 OrderBook、MatchingEngine、Trade、Position、Ledger 等核心领域对象，保证订单生命周期、成交、费用、冻结和账户更新的一致性。

6. PostgreSQL 持久化与研究证据层  
   保存 orders、trades、snapshots_1s、bars_1m、training_episodes、model_transitions、evidence_artifacts 等运行事实和研究证据。

## 5. 前后端边界与桌面端设计要点

论文中应强调：虽然系统是单进程桌面应用，但仍具有清晰的前后端边界。

前端职责：

- 展示市场、订单、账户、agent、Arena 和 Evidence Board 状态。
- 收集用户操作，例如创建标的、提交订单、启动 agent、运行 Arena。
- 通过 adapter 和 controller 调用 RuntimeGateway。

前端不应承担的职责：

- 不直接判断订单是否可成交。
- 不直接修改账户资金或持仓。
- 不直接打开 runtime ORM session。
- 不把缺失数据或缓存数据伪装成 runtime truth。

后端职责：

- 维护订单簿、撮合引擎、账户、持仓、时钟和交易规则。
- 生成订单事件、成交事件、账户事件和市场快照。
- 通过 PostgreSQL 保存运行事实。
- 为 Evidence Runner 提供可读回的 runtime/database facts。

可写结论：

> UTI-STOCKSIM 的桌面前端不是业务逻辑中心，而是 runtime truth 的观察与控制入口。系统通过 RuntimeGateway 把 UI 操作与交易运行时隔离，使用户界面、应用服务和后端交易语义之间保持清晰边界。

## 6. 真实交易语义 Runtime 应写的内容

第四章可以重点写以下内容：

- 订单生命周期：NEW、PARTIALLY_FILLED、FILLED、CANCELLED、REJECTED。
- 买入订单路径：模型或 retail agent 生成买入意图，经 Action Contract 转成标准订单，进入风控校验，账户冻结资金和预估费用，订单进入撮合引擎，成交后生成 trade，并由账户服务扣除真实成交成本、释放或退还冻结金额。
- 卖出订单路径：校验可卖数量、T+1、持仓冻结，成交后减少持仓并增加现金。
- 撮合规则：订单簿维护买卖委托，按价格优先、时间优先撮合，支持部分成交和完全成交。
- 账户语义：现金、冻结资金、持仓、可卖数量、费用、ledger 流水必须与订单状态一致。
- 事件与 K 线：订单、成交和账户更新通过事件总线传递，快照写入 snapshots_1s，再聚合 bars_1m 等 K 线。

论文中可强调：

> 模型训练中的 action 不能直接变成收益，而必须经过订单校验、账户冻结、订单簿撮合、成交结算和费用扣除。这使训练结果更接近真实交易约束，也降低模型利用理想化环境漏洞的风险。

## 7. Retail Agent 行为生态应写的内容

第五章应把 retail agent 写成“市场背景生态”，而不是简单随机交易脚本。

可写组成：

- 行为家族：trend_follow、mean_revert、buy_the_dip、profit_taking、liquidity_noise。
- 性格参数：risk_preference、loss_aversion、courage、patience、price_sensitivity。
- 状态变量：cash、position、sellable_qty、unfilled_orders、recent_pnl、holding_period。
- Calibration 指标：buy_sell_ratio、two_sided_book_coverage、trade_presence、holding_period、retail_family_mix。

可写作用：

- 为 model agent 提供更接近真实市场的背景噪声和流动性。
- 避免训练世界过于干净，导致模型只在理想环境下有效。
- 通过 calibration 指标检查市场是否有双边订单、成交活跃度和合理行为分布。

- K 线事实链路已恢复并纳入 live Evidence Runner。
- MarketMetricsExtractor 字段适配与派生逻辑已修复。
- Calibration artifact 已达到 `pass_gate=true / engineering_pass=true`，P0 指标无 missing/failed。

## 8. Model Agent 与 Arena 训练机制应写的内容

第六章可以围绕“模型如何接入 runtime”展开。

模型接入原则：

- 模型只能通过 Observation / Action / Reward Contract 与 runtime 交互。
- 模型不能直接访问 GUI、数据库表、撮合引擎内部状态或账户结果。
- action 必须转换为标准订单，由 runtime 决定是否成交和如何结算。

Observation 可写结构：

- market：盘口、成交、价格、K 线等市场信息。
- account：现金、持仓、冻结、权益等账户信息。
- context：交易日、时钟、episode、run_id 等上下文。
- features：派生指标，但应与 runtime truth 区分。

Arena 作用：

- 创建训练场景、world_spec 和 random_seed。
- 创建 retail population 和多个 model agent。
- 启动 episode，收集 transitions。
- 汇总 model_episode_results。
- 保存 checkpoint 和 lineage。
- 通过 Evidence Runner 审查模型是否可成为父代或进入研究结论。

PBT 写作边界：

- PBT 不能只按 leaderboard 收益选父代。
- 高收益模型必须通过 calibration、hidden evaluation、exploit test、paired sensitivity 等证据。
- Strict Parent Gate 把父代资格从“收益最高”升级为“证据门控资格”。

## 9. PostgreSQL 与 run_id 实验事实边界

第七章应强调 PostgreSQL-first 和 run_id 的意义。

PostgreSQL 保存两类事实：

1. 交易业务事实：
   accounts、positions、ledgers、instruments、orders、order_events、trades、snapshots_1s、bars_1m、bars_1h、bars_1d、event_log。

2. 训练研究事实：
   simulation_runs、agent_bindings、account_equity_snapshots、training_episodes、model_episode_results、model_transitions、model_checkpoints、model_lineage、evidence_artifacts。

run_id 的作用：

- 区分不同仿真实验，避免同一标的在不同运行中的数据混淆。
- 让订单、成交、K 线、训练 episode 和 evidence artifact 归属于同一实验事实边界。
- 支持回放、审计、对比和 Evidence Runner 聚合。

当前项目状态：

- 正式 runtime 默认使用 PostgreSQL。
- SQLite 主要用于测试、demo 和轻量诊断。
- PostgreSQL driver 路径已修复，支持 pg8000 fallback。
- 后续仍需正式数据库迁移治理工具，当前 schema guard 更偏工程过渡态。

## 10. Evidence Runner 与证据门控应重点写

第八章是论文中最能体现项目研究价值的部分。

Evidence Runner 的核心思想：

> 模型研究结论不能只由收益曲线或 leaderboard 决定，而必须由多项独立 evidence artifact 共同支持。

主要证据项：

- baseline_artifact：候选模型相对规则基线是否具备合理表现。
- calibration_artifact：市场质量和 retail 背景是否达到工程验收要求。
- hidden_eval_artifact：候选模型是否能在隐藏世界中保持表现，降低过拟合风险。
- exploit_test_artifact：候选模型是否利用费用、时钟、成交或边界漏洞获得不可交易收益。
- paired_sensitivity_artifact：在 high_fee、high_impact、low_liquidity 等场景下是否表现合理退化。
- parent_gate_artifact：是否具备 PBT 父代资格。
- research_acceptance_lock：是否打开 level-1 research acceptance lock。

Strict Aggregate 应写：

- 它读取 evidence records，不重新运行模型。
- 检查 required evidence 是否存在、是否通过、是否具备当前 schema 和 strict fields。
- 旧格式 artifact 即使写着 pass_fail=true，如果缺少 source、runner_version、artifact_hash、source_run_ids、pass_gate 等字段，也不能当作当前有效证据。

Model Route Gate 应写：

- 防止在证据不足时提前升级 Transformer、GTrXL、复杂 MARL、historical replay、hybrid env 或 alpha-claim。
- 当前 level-1 go 不等于复杂路线全部放开，仍需按证据层级逐步推进。

## 12. 论文可写主要贡献

建议在摘要、绪论和结论中写成五点：

1. 构建真实交易语义 runtime  
   系统将订单簿、撮合、账户、资金冻结、费用、T+1、卖空约束、事件和 K 线纳入统一运行时。

2. 构建锚定 retail 行为生态  
   通过行为家族、性格参数、状态变量和 calibration 指标形成稳定但有噪声的背景市场。

3. 设计模型契约化交互机制  
   Model agent 通过 Observation / Action / Reward Contract 接入 runtime，避免绕过交易规则。

4. 建立 Arena/PBT 训练闭环  
   支持多模型 episode、transition 收集、episode result、checkpoint、lineage 和父代继承。

5. 引入 Evidence Runner 证据门控  
   将模型研究判断从 leaderboard 收益提升为 baseline、hidden、calibration、exploit、paired sensitivity、parent gate 和 research lock 等多项证据审查。

## 13. 论文必须保留的研究边界

为了避免论文结论过度，以下边界必须写清楚：

- 本文证明的是仿真实验平台、真实 runtime evidence package 生成能力和 level-1 engineering acceptance。
- 本文不证明某个交易模型已经具备真实市场盈利能力。
- 本文不证明 alpha claim。
- 本文不证明真实市场迁移可行。
- 当前 `research_claim_eligible` 仍不是通过状态。
- 复杂模型路线仍应由 Model Route Gate 按证据层级约束。
- PostgreSQL-first 已经落地，但正式数据库迁移治理仍可作为后续工作。
- Redis hot-state 层尚未落地，可作为未来优化方向。

推荐结论句：

> 本文的实验结果证明 UTI-STOCKSIM 已具备真实 runtime/database 证据生成、结构化证据聚合和 level-1 工程验收放行能力；但该结论仍限定于工程验收层级，不应被解释为真实市场盈利能力或高层级研究结论。
